## Verdict

**NOT READY FOR BLOCK 2 / Linux production-hardening.** AD MTP remains fail-closed. The blocker is precise and reproducible: k5 first diverges inside batched target verification before commit/replay; diagnostic row-wise linear and sequential GDN guards can restore one short cycle but do not preserve full-generation state or output parity.

## Evidence

- AD IQ2_S/IQ4_NL RAW is 51.84–52.58 TG in the archived 16K matrices. There is no evidence of an AD RAW baseline above 68 TG; the historical >68 values are AD MTP runs with different output SHA. The requested “RAW >68” target is therefore a model/path label mismatch, not a demonstrated regression.
- Corrected k5 trace: first two target rows match RAW, the third differs before commit. The first projection difference is the layer-0 MLP hyper-connection input; batched GEMM reduction order and batched GDN recurrence both contribute.
- `FREETOKEN_VERIFY_ROWWISE_LINEAR=1` plus `FREETOKEN_GDN_VERIFY_SEQUENTIAL=1` restores one oracle cycle's logits/state parity. A full 16K k5 run still diverges later.
- Torch HC reference recovers one cycle's argmax only. Full decode32 remains divergent: RAW `a59f7ed31d3a`, MTP `7250748f8115`.
- Existing QSA transaction repair addresses the compressed ratio-4 page boundary and focused transaction tests pass, but it does not prove the remaining batched verify/state transition.

## Root cause and classification

Classification: **REAL_STATE/ALGORITHM_BUG**, with low-margin **BENIGN_FP_DIVERGENCE** as the trigger. CUDA graphs are not the sole cause; disabling graphs still diverges. The unresolved mechanism is the batched verify path's interaction between row mapping, reduction order, GDN recurrence, hyper-connection inputs, and committed state after the verify transaction.
